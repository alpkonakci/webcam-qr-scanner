## Beta.2 acceptance and phone delivery UX follow-up — 2026-10-03

- The user confirmed pairing persistence after a PC reboot, reopening the phone
  page through Open scanner on phone, and Send to PC without re-pairing. The
  supplied confirmation screenshot names My iPhone; no Android reboot evidence
  was added by this test.
- With QR Scanner fully exited, the phone reported receiver offline. Reopening
  the desktop app and sending again succeeded. With the app left open and PC
  Wi-Fi disconnected for 90 seconds, the same offline error was reported; after
  reconnecting Wi-Fi, waiting 60 seconds and explicitly sending again, the PC
  prompt appeared and the user-approved HTTP link opened. These are user-attested
  recovery checks, not instrumented proof of the forced Realtime fallback path.
- An earlier network-cut attempt timed out on the phone but arrived at the PC
  on reconnection. Source explains the possible late arrival: the phone waits
  15 seconds for a receipt, while an accepted envelope can remain queued for
  five minutes. It is not automatically cancelled by the phone timeout. The
  exact timing of that earlier send was not recorded.
- Phone UX now distinguishes an unconfirmed delivery from a definite offline
  rejection. A pending result locks Send to PC and offers Check delivery status,
  which performs only a GET for the existing delivery. A page-memory attempt
  registry also coalesces simultaneous taps and rescans of the same URL/pair.
  Lost POST responses remain uncertain and cannot silently create another POST.
  Only a verified encrypted receipt is labelled received; PC URL approval stays
  unchanged. This is not an automatic cancellation feature.
- The registry is ephemeral: page reload/closure clears it, and it does not
  guard independent tabs. The pending message asks users to keep the page open.
  No URL, token or receipt data is newly persisted in browser storage.
- Camera help explains the browser-controlled per-site permission, separate
  from pairing. Camera remains closed on page load, opens only after Scan QR,
  and is destroyed when scanning closes. No permission setting is changed.
- Local verification: 42 PWA tests, production build/TypeScript and ESLint passed;
  generated browser assets passed secret scanning. Pending/checking/delivered
  markup was render-tested; a 390px mobile pending fixture was visually checked.
  Real-phone acceptance of the new pending-status button remains open. No
  desktop code, published ZIP, checksum or beta.2 tag is changed by this hotfix.
